# 主菜单功能插件接入规范

> 适用范围：以 MainMenu 为依赖、往主菜单上挂功能的插件（`./Minecraft-26_3-plugin/<插件名>/`）。
> 目标：功能插件只声明「怎么显示 / 点击做什么 / 默认位置」，位置、排序、分页、冲突与管理界面全部交给 MainMenu。

本规范写给**以 MainMenu 为依赖的后续插件**：把你的功能挂到主菜单上，由玩家通过 ESC 菜单按钮 / `/cd` 命令 / 手持时钟右键打开。

主菜单本体（界面、分页、翻页、位置冲突、管理员管理界面）全部由 MainMenu 负责，功能插件只提供五件事：

| 要素 | 对应 API | 说明 |
| --- | --- | --- |
| 用什么物品显示 | `icon(...)` | 材质或 `ItemStack`；完整物品用于背包回退，ArcMenu 的显示边界见下文 |
| 鼠标悬停显示什么文本 | `name(...)` / `line(...)` / `lines(...)` | MiniMessage 文本，可多行 |
| 点击是否有效 | `clickable(true/false)` | 默认 `false`（纯展示，点了没反应） |
| 点击后做什么 | `onClick((player, clickType) -> ...)` | 设置后自动视为可点击 |
| 显示位置（可选） | `preferredSlot(int)` | 0~53，且必须是**功能区以外**的格子；不设置则进功能区 |
| 功能区排序（可选） | `order(int)` | 越小越靠前，默认 `0`（按注册顺序） |

功能的位置、排序、显示 / 隐藏、是否固定位置，玩家侧管理员都可以在游戏里随时调整（见第 5 节），
所以插件声明的只是**默认值**，不要指望它一直生效。

---

## 1. 依赖与加载顺序

### 1.1 `paper-plugin.yml`

```yaml
name: Shop
version: '${version}'
main: com.example.shop.ShopPlugin
api-version: '26.3'
# Folia 必须声明，否则插件会被拒绝加载
folia-supported: true

# 关键：声明依赖 MainMenu，保证它先加载，才能在 onEnable 里注册功能
dependencies:
  server:
    MainMenu:
      load: BEFORE
      required: true
```

`required: true` 表示主菜单缺失时你的插件不会加载（推荐，避免注册失败）。
若希望主菜单缺失时仍能运行，用 `required: false`，并在注册前判断 `MainMenuApi.isAvailable()`。

### 1.2 `build.gradle`

同一个仓库内的插件直接依赖工程即可（只用于编译，运行期由服务端提供 MainMenu 的类）：

```groovy
version = '0.1.0'

dependencies {
    compileOnly project(':MainMenu')
}
```

不同仓库时把 MainMenu 的 jar 放进 `./libs/` 或发布到私有仓库，同样用 `compileOnly`（**不要** `implementation`，否则会打进你自己的 jar 造成类冲突）。

## 2. 注册一个功能

```java
package com.example.shop;

import com.example.mainmenu.api.MainMenuApi;
import com.example.mainmenu.api.MenuFeature;
import net.kyori.adventure.text.Component;
import org.bukkit.Material;
import org.bukkit.entity.Player;
import org.bukkit.plugin.java.JavaPlugin;

public final class ShopPlugin extends JavaPlugin {

    @Override
    public void onEnable() {
        MainMenuApi.registry().register(
                MenuFeature.builder("shop:main")          // id：建议 "<插件名>:<功能名>"
                        .owner(getPluginMeta().getName())  // 可选，默认取 id 里 : 之前的部分
                        .icon(Material.EMERALD)            // 用什么物品显示
                        .name("<green>商店</green>")        // 物品显示名
                        .line("<gray>点击打开商店</gray>")   // 悬停文本（可多行）
                        .onClick((player, clickType) -> openShop(player))  // 点击做什么
                        .build());
    }

    @Override
    public void onDisable() {
        // 插件卸载/重载时把功能摘掉，避免留下悬空引用
        MainMenuApi.registryOrNull().unregister("shop:main");
    }

    private void openShop(final Player player) {
        player.sendMessage(Component.text("打开商店"));
    }
}
```

约定与校验：

- `id` 必须唯一，重复注册会被拒绝（`IllegalArgumentException`）；建议 `"<插件名>:<功能名>"` 便于排查。
- `icon` 不能是空气；不设置时默认石头。
- `clickable(true)` 但没写 `onClick` 会在 `build()` 时报错；`onClick` 会自动把功能标记为可点击。
- `name` 不设置时用 `id` 当显示名。
- 注册时机放在自己的 `onEnable()`：主菜单只保存引用，渲染时才调用 `icon()` / `description()`。
- 除了 `MainMenuApi.registry()`，也可以走 Bukkit 服务系统：`Bukkit.getServicesManager().load(MenuFeatureRegistry.class)`。

### 动态文本

`icon()` 与 `description()` 在**每次渲染时**都会被调用（菜单打开期间默认每秒重绘一次，见 `menu.refresh-seconds`），
所以时间、余额、冷却这类会变的内容可以直接实时算 —— RealTime 插件的「当前时间」就是这么做的。

> 注意：这两个方法**不带玩家上下文**，功能文本是全局的（所有人看到的一样）。
> 需要按玩家变化的文本，用下面的「按查看者渲染」，或让功能在点击后自行刷新（`player.sendMessage(...)`）。

### 按查看者渲染（显示"查看者自己的数据"）

需要「每个玩家看到自己的数据」（例如自己的头像、自己的在线时长）时，覆写这两个重载 ——
它们是 `MenuFeature` 的 default 方法，不覆写时行为与原来完全一致：

| 方法 | 作用 |
| --- | --- |
| `icon(Player viewer)` | 按查看者渲染图标，例如查看者自己的头（`PLAYER_HEAD` + `setOwningPlayer(viewer)`） |
| `description(Player viewer)` | 按查看者渲染悬停文本 |

用构建器时对应 `iconForViewer(...)` / `linesForViewer(...)`：

```java
MainMenuApi.registry().register(
        MenuFeature.builder("shop:my-balance")
                .icon(Material.GOLD_INGOT)                                  // 静态兜底（注册校验用，不能是空气）
                .iconForViewer(viewer -> playerHead(viewer))                // 每次渲染现算
                .linesForViewer(viewer -> List.of(
                        Component.text("玩家：" + viewer.getName()),
                        Component.text("余额：" + balanceOf(viewer))))
                .build());
```

- `viewer` 是**正在看菜单的玩家**；功能管理界面里是**管理员**（他看到的也是他自己的数据，排查时注意）。
- 每次渲染都会调用（默认每秒重绘一次），数字会跟着走，不需要自己起刷新任务。
- 返回值按原样写入物品；位置冲突、点击提示仍由主菜单追加在最后。
- 别在渲染路径里做阻塞 IO（网络、大文件）；读内存或本地缓存。
- 参考实现：伴侣插件 `./Minecraft-26_3-plugin/YudreamPlaytime/`（查看者自己的头 + 在线时长 / 挂机时长）。

### 打开主菜单（功能插件自己的界面里做「返回上一级」）

功能插件在自己的 GUI 里需要「返回主菜单」时，直接调用：

```java
MainMenuApi.open(player);        // 主菜单未加载时抛异常
MainMenuApi.openOrNull(player);  // 主菜单不可用时返回 false，不抛异常
```

它等价于玩家自己执行 `/cd`（打开第一页），MainMenu 启动时把自己的打开入口注册进去。

> 注意：这是"打开菜单"，不是"返回上一页"。功能插件自己的翻页状态由自己维护；回到菜单总是第一页。

## 3. 布局与位置规则

自 MainMenu `Beta_1_6_0` 起，安装 ArcMenu 3.2 时首页和配套页面使用原生 YAML。
首页的布局、标题、配色、模型和按钮动作由服务端管理员编辑，功能插件仍按本规范注册，无需依赖 ArcMenu。
配置与显示边界见 `./Minecraft-26_3-plugin/MainMenu/README.md`：默认手机应用抽屉与管理页使用动态材质、名称与悬停信息，
背包回退保留完整 `ItemStack`；不要假设任意物品元数据都能直接转换为 ArcMenu 模型。

以下 6×9（54 格）是注册 API、管理位置选择和背包回退共用的**逻辑位置规则**，
手机应用抽屉按逻辑页、位置读取可见功能，以 12 项/页显示；不限制 YAML 页面的视觉布局。`slot` 为 0 基编号：

```
第1行   [ 0]空位   [ 1]时间*  [ 2]空位   [ 3]空位   [ 4]空位   [ 5]空位   [ 6]空位   [ 7]空位   [ 8]空位
第2行   [ 9]空位   [10]空位 …… （第 2 行整行空位）
第3行   [18]空位   [19]功能区 [20]功能区 [21]功能区 [22]功能区 [23]功能区 [24]功能区 [25]功能区 [26]空位
第4行   [27]上一页 [28]功能区 [29]功能区 [30]功能区 [31]功能区 [32]功能区 [33]功能区 [34]功能区 [35]下一页
第5行   [36]空位   [37]功能区 [38]功能区 [39]功能区 [40]功能区 [41]功能区 [42]功能区 [43]功能区 [44]空位
第6行   [45]空位   [46]空位   [47]空位   [48]空位   [49]管理入口 [50]空位  [51]空位  [52]空位  [53]空位
```

- **固定功能位**（`27` 上一页、`35` 下一页、`49` 管理入口）：任何插件都不能占用，`49` 只有管理员看得到、点得动，其他玩家那一格是普通空位。
- **非固定功能位**（其余所有功能区以外的格子，默认显示白色染色玻璃板）：功能插件可以用 `preferredSlot` 占用。
- **功能区**：第 3~5 行、第 2~8 列，共 **21 格**，由主菜单按排序值填充，可翻页。

> 第 1 行第 2 格（`slot 1`）常规留给「当前时间」，由 RealTime 插件用 `preferredSlot(1)` 占用（图中 `时间*`）。
> 它和别的空位一样是**先到先得**，技术上谁都能占，只是别去抢它。

### 3.1 不设置位置

按 `order` 排进功能区，第 1 页放满 21 个后自动进第 2 页，依此类推。这是绝大多数功能该有的样子。

### 3.2 自定义位置

```java
.preferredSlot(0)   // 第 1 行第 1 格（空位，允许）
.preferredSlot(1)   // 第 1 行第 2 格（空位，RealTime 在用）
.preferredSlot(19)  // 功能区格子 —— 视为“没声明位置”，按排序值进功能区，不算冲突
.preferredSlot(99)  // 越界 —— 同上，视为“没声明位置”
.preferredSlot(27)  // 固定功能位（上一页）—— 冲突，见 3.3
```

也就是说：**只有功能区以外的格子才算自定义位置**，声明在功能区里等于没声明。

### 3.3 冲突处理

以下情况判定为**位置冲突**：

1. 与固定功能位冲突（`27` / `35` / `49`）；
2. 该格子已被其它插件的自定义位置占用（先注册者优先）。

冲突时不会报错，也不会挤掉别人，而是：**该功能自动排进功能区**（排在同页最前面），并在它的悬停文本最后追加一行：

```
该功能插件位置不可用，已自动归到功能区
```

这行文案可在 MainMenu 的 `config.yml` → `menu.feature.conflict-hint` 修改。

### 3.4 固定位置功能插件

声明了功能区以外 `preferredSlot` 的功能，在 MainMenu 眼里属于**固定位置功能插件**：

- 它在管理界面里出现在**右栏**（左栏是非固定位置功能插件，即排功能区的那些）；
- 它的位置每页都显示（不随翻页消失）；
- **位置冲突时它依然算固定位置功能插件**（位置记录保留、仍在右栏），只是显示上被改排到功能区最前面；
- 管理员可以把它改成非固定位置功能插件，也可以再改回来（改回来会还原原来的位置）。

不需要固定位置的功能，**不要**写 `preferredSlot`，让它按 `order` 进功能区即可。

### 3.5 分页

- 每页功能区 21 格，页数 = `ceil(功能区功能数 / 21)`，至少 1 页。
- 自定义位置的功能不在功能区，每页都会显示。
- 翻页只用主菜单自带的箭头（第 4 行第 1 / 第 9 格），功能插件不需要关心分页。

### 3.6 排序

功能区先按 `order(int)` 升序排列，`order` 相同的再按注册顺序（稳定排序）。默认 `order = 0`。

注意：**跨插件的"注册顺序"等于服务端的插件加载顺序，由服务端决定，不一定是字母序**（实测 Folia 26.3 按插件名逆序加载）。所以：

- 想让自己的功能稳定排在某个位置，用 `order(...)`（例如 `order(10)`、`order(20)`，留出间隔方便以后插入）；
- 想固定占某一格，用 `preferredSlot(...)`；
- 同一个插件内注册多个功能时，它们之间的先后就是代码里的注册顺序。

## 4. 交互约定

- 菜单里的物品**一律不可移动**（含 shift 点击、拖拽、数字键交换），主菜单会取消这些操作。
- 只有 `clickable(true)` 的功能会收到点击回调，回调参数是 `(Player, ClickType)`，可据此区分左键 / 右键 / shift。
- 点击回调在**查看者所属区域线程**执行（Folia 的 `player.getScheduler()` 线程），可以安全地操作该玩家的世界、打开其它 GUI、发消息；
  不要假设存在“主线程”，也不要在回调里直接操作其它玩家或远处方块。
- 回调里抛出的异常会被主菜单捕获并记入日志，不会影响其它功能。
- MainMenu 负责展示功能信息并转发点击；ArcMenu 的标题、布局、模型和命中区域由 YAML 控制，背包回退由原渲染器控制，功能插件不用管理这些界面细节。

## 5. 管理员能在游戏里改什么

管理员（权限 `mainmenu.admin`，默认 OP）从 ArcMenu 手机桌面“桌面管理”进入；背包回退从第 6 行第 5 格命令方块进入。可以对**任何**功能（含你的）做这些事（表内格子和物品描述适用于背包回退）：

| 操作 | 效果 |
| --- | --- |
| 添加功能占位符 | 在管理页第 1 行第 1 格（漏斗）点击；在功能区末尾添加一个占位符，管理页左栏用红色玻璃板显示，主菜单不显示 |
| 添加自定义插件功能 | 在管理页第 1 行第 3 格（书与笔）点击；输入名称后创建默认纸图标的正常功能，外观/点击指令在 `custom-features.yml` 配置，管理页可像其它功能一样显示/隐藏、排序、转固定位置 |
| 显示 / 隐藏 | 隐藏的功能不显示，**也不占用它的位置** —— 原来与它冲突的插件会恢复正常显示 |
| 调整排序值 | 覆盖插件声明的 `order` |
| 转为固定位置 | 从功能区挪出来变成固定位置功能插件；此前设置过位置的会回到原来的位置，从来没设置过位置的默认放到第 1 行第 1 格 |
| 更改位置 | 在"位置选择界面"里点一个空位（功能区与翻页位置不能选） |
| 转为非固定位置 | 变回按排序值排进功能区的普通功能 |

这些改动保存在 `plugins/MainMenu/features.yml`，重启服务端后仍然有效，**并且优先于插件自己声明的值**。

> 管理页的「添加功能占位符」是 MainMenu 自己的管理工具，不是插件 API：占位符参与功能区排序与分页，
> 但主菜单渲染时跳过；点击占位符只有“调整排序值”和“删除”两个操作。功能插件不需要、也不应该去读写占位符。
>
> 「添加自定义插件功能」创建的也是 MainMenu 内部功能（默认纸图标），定义在 `plugins/MainMenu/custom-features.yml`；
> 它在管理页与普通功能走同一套配置逻辑，但功能插件不需要、也不应该去读写这个文件。

对插件作者的三个含义：

1. 插件声明的位置 / 排序只是初始值，别在插件里写"必须在某格"的逻辑；
2. 不要自己再去读写 `features.yml`，那是 MainMenu 的内部状态；
3. 你的功能被管理员隐藏后，`onClick` 不会被调用（界面里根本没有它），插件侧不需要做额外处理。

## 6. 参考实现：RealTime 插件

`./Minecraft-26_3-plugin/RealTime` 就是本仓库里的一个标准功能插件，用 `preferredSlot(1)` 占住第 1 行第 2 格显示当前时间：

```java
MainMenuApi.registry().register(
        MenuFeature.builder("realtime:clock")
                .icon(clockItem)                       // 时钟物品
                .name("<white>当前时间</white>")
                .line("<gray>当前时间：<white>" + now() + "</white></gray>")  // 每次渲染重新算
                .preferredSlot(1)
                .build());
```

完整源码（含配置项、时区与格式处理）见 `./Minecraft-26_3-plugin/RealTime/src/main/java/com/example/realtime/TimeFeature.java`。

## 7. 自查

主菜单提供了 `/cd debug`（权限 `mainmenu.reload`），会输出：

- 内置数据包与 ESC 菜单按钮（`pause_screen_additions` 标签）状态；
- 功能总数与分类（固定位置 / 非固定位置各几个）；
- 每个功能最终落在哪一格、第几页、是否因冲突被改排；
- 6 行 × 9 列的布局预览（`[槽位]名称`）；
- 配置文本自检。

注册后执行一次 `/cd debug`，确认自己的功能出现在预期格子上即可。

## 8. 常见问题

| 现象 | 原因 / 处理 |
| --- | --- |
| 服务端提示插件不支持 Folia / 插件根本没加载 | `paper-plugin.yml` 缺 `folia-supported: true` |
| `IllegalStateException: MainMenu 尚未加载` | `paper-plugin.yml` 里没声明 `dependencies.server.MainMenu`（或 `load` 不是 `BEFORE`） |
| `IllegalArgumentException: 功能 id 重复` | 换一个 `id`（或先 `unregister` 旧的） |
| `build()` 抛"标记为可点击，但没有设置 onClick" | 要么补 `onClick`，要么去掉 `clickable(true)` |
| 悬停文本末尾出现"该功能插件位置不可用，已自动归到功能区" | 声明的 `preferredSlot` 是固定功能位、或已被别的插件占用；改声明位置，或干脆不声明 |
| 功能位置和写的不一样 | 管理员在管理界面改过（`features.yml` 优先），用 `/cd debug` 看实际位置 |
| 排在前面的功能每次重启都变 | 跨插件注册顺序取决于服务端加载顺序，用 `order(...)` 固定 |

## 9. 手机两侧卡片
